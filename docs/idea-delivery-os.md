# 最终产品定义：想法 → 交付 的产品研发 OS（v1，2026-08-30）

> 用户原话："任何一个想法进来后，比如今天我要做一个扫地机器人，我们也能完整的做交付。"
> 本文档定义最终产品形态。LiteCool S1（桌面小空调）是本 OS 的**第一个 dogfood 实例**。

## 1. 产品是什么

一套**硬件产品研发交付操作系统**：任意一个产品想法进来，经过 S0–S9 流水线，交付一套
"可以直接进入打样与供应链谈判"的完整资产包。agent 团队是引擎，流水线是骨架，数据闸是质量体系，
工作台是控制室，人类只在决策点（S7）介入。

## 2. 完整交付合同（任何想法的九件套）

| # | 交付物 | 消除的不确定性 |
|---|---|---|
| 1 | 需求基线（硬约束+功能需求+非目标+验收标准） | 做错东西 |
| 2 | 产品定义书（规格带测量条件） | 口径漂移 |
| 3 | 竞品证据包（实抓数据：价格/销量/评价原文/形态） | 拍脑袋定位 |
| 4 | 专利预检索 + 逐方向规避设计 | 法律风险 |
| 5 | BOM + 供应商映射（核验分级）+ 成本核算 | 商业不成立 |
| 6 | 形态方向稿 + 概念视觉（人类选美） | 设计 naive |
| 7 | 工程装配体（DFM 级，逐零件挂 BOM）+ 解构图鉴 | 结构与制造 |
| 8 | 验证计划（手板实测项与退出条件） | 物理不达标 |
| 9 | RFQ 询价包 + NDA + 受控外发包 | 供应链对接 |

质量底线（dogfood 实证）：数据实抓非编造（空壳率闸）、专利逐条可复核、供应商真实旺旺记录、
3D 按真实规格尺寸、所有决策留痕（decisions.json）。

## 3. 新想法接入仪式（S0）

1. 人类给一句话想法（如"做一个扫地机器人"）→ 立项：`projects/<idea-slug>/` 从模板脚手架生成
   （schemas/阶段定义/文档模板/Rfq 模板/验证计划模板——LiteCool S1 的结构即模板）；
2. S0 访谈式需求基线：硬约束（品类/预算/禁做项）必须由人类拍板，其余 agent 推导标 [D]；
3. 进入标准流水线 S1–S9；每个 S 阶段的执行 playbook 复用（竞品实抓/专利检索/1688 询价/
   概念图 prompt 工程/Blender 装配/AI 皮肤/图鉴/RFQ——全部是 dogfood 验证过的可复用序列）；
4. S7 人类验收 = 唯一必须的人类动作；其余阶段 agent 自治 + 数据闸把关。

## 4. 系统架构决策（v1 → v2 路线）

**v1（当前，单项目）**：Python 流水线 + JSON 数据快照 + 无构建链 ES-module 工作台（只读）。
已交付，继续维护。

**v2（多项目产品化，择机启动）**——触发条件（满足任二）：① 第二个想法立项；② S7 决策要在 UI 里
直接批注（写操作）；③ 多 agent 运行状态需要实时看板。

- **后端**：薄本地服务（Python FastAPI，`pipeline/` 同源）——项目注册表（projects/ 索引）、
  数据快照 API、决策写 API（S7 批注落 decisions.json）、agent 运行状态（session-forensics
  progress_probe 数据源）。无多用户/无云部署（本地优先）。
- **前端**：迁移 React + Vite——**只有 v2 触发时才迁**。理由：当前只读六视图用原生 ES-module
  已验证且零依赖；React 的收益（组件生态/状态管理/表单）在写操作与多项目场景才兑现。
  迁移成本已被压低：组件 registry、tokens、视图与数据映射在 v1 已组件化，平移而非重写。
- **不选的**：现在切 React（speculative generality——为一个还没立项的第二个想法重构，违反
  "微小改动"与 KISS）；云端多租户（超出当前所有需求）。
